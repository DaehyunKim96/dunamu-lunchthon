Concept 1

Connect to GIWA Chain

블록체인 앱은 먼저 어느 네트워크에 연결할지 알아야 합니다. GIWA Sepolia는 실제 서비스 배포 전 컨트랙트와 트랜잭션을 테스트하는 테스트넷입니다. 사용자는 지갑에서 GIWA Sepolia 네트워크를 추가하고, 프론트엔드는 RPC URL을 통해 체인 데이터를 읽고 트랜잭션을 보냅니다.

항목 값 의미
Chain ID 91342 지갑과 앱이 GIWA Sepolia를 식별하는 번호입니다.
RPC https://sepolia-rpc.giwa.io 블록, 계정, 트랜잭션 데이터를 읽고 쓰는 진입점입니다.
Flashblocks RPC https://sepolia-rpc-flashblocks.giwa.io 더 빠른 preconfirmation UX를 구현할 때 활용할 수 있습니다.
Explorer https://sepolia-explorer.giwa.io 배포된 컨트랙트와 트랜잭션 결과를 확인하는 화면입니다.
이 제품에 적용한 방식 프론트엔드 설정 파일에 GIWA Sepolia 정보를 넣었습니다. 나중에 wagmi나 viem을 붙이면 이 설정을 기준으로 지갑 네트워크 전환, contract read, transaction write를 처리할 수 있습니다.

Concept 2

GIWA Contracts

GIWA Contracts 문서는 GIWA Sepolia 위에서 이미 사용할 수 있도록 배포된 주요 컨트랙트 주소를 모아둔 문서입니다. 어렵게 들리지만, 쉽게 말하면 “GIWA 체인에서 자주 쓰는 공용 기능들의 주소록”입니다.

여기서 말하는 주소들은 우리가 만든 티켓 서비스의 컨트랙트 주소가 아닙니다. GIWA 생태계가 미리 준비해 둔 공용 컨트랙트 주소입니다. 예를 들어 지갑을 더 안전하게 운영하는 기능, 여러 데이터를 한 번에 읽는 기능, 검증 정보를 확인하는 기능, 사람 이름처럼 보이는 지갑 이름을 찾는 기능 등이 여기에 포함됩니다.

먼저 용어부터 쉽게 정리하면:
컨트랙트는 블록체인 위에서 실행되는 프로그램입니다. 컨트랙트 주소는 그 프로그램이 배포된 위치입니다. 인프라 컨트랙트는 여러 서비스가 같이 쓰는 공용 프로그램입니다. 우리 제품은 이 공용 프로그램들을 직접 새로 만들지 않고, 이미 배포된 주소를 불러와 사용합니다.
문서 속 분류 대표 예시 쉽게 말하면 이 제품에서의 의미
Pre Installs Safe, Multicall3, Permit2, EntryPoint GIWA가 미리 준비해 둔 기본 도구 상자입니다. 지금 MVP의 핵심은 아니지만, 나중에 운영자 지갑을 더 안전하게 만들거나 여러 조회를 한 번에 묶을 때 쓸 수 있습니다.
System WETH9, Bridge, GasPriceOracle, EAS 체인이 돌아가는 데 필요한 기반 기능입니다. Dojang의 검증 기록은 EAS라는 시스템과 연결되어 있습니다. 우리 제품은 보통 간편 조회용 DojangScroll을 쓰지만, 깊은 감사가 필요하면 EAS 원본을 확인할 수 있습니다.
Dojang DojangScroll, AttestationIndexer “이 지갑이 검증된 지갑인가?”를 확인하기 쉽게 만든 기능입니다. 티켓을 사는 사람과 양도받는 사람이 Verified Address인지 확인하는 핵심 기능입니다.
Playground UPNameRegistry 사용자 경험을 더 좋게 만들기 위한 기능입니다. 팬을 긴 지갑 주소 대신 minjun.up.id처럼 사람이 읽기 쉬운 이름으로 보여줄 수 있습니다.
은행 앱에 비유하면 GIWA Contracts 문서는 은행 앱이 사용하는 공용 시스템 목록과 비슷합니다. 예를 들어 본인확인 시스템, 계좌 조회 시스템, 송금 시스템의 주소를 알아야 은행 앱이 동작합니다. 우리 티켓 앱도 마찬가지입니다. 검증 조회는 DojangScroll에 묻고, 검증 기록의 원본은 EAS에 있으며, 지갑 이름은 UPNameRegistry에서 찾습니다.

DojangScroll 검증 조회

한 줄로 말하면, DojangScroll은 “이 지갑이 검증된 지갑인지” 물어보는 창구입니다. 우리 서비스는 사용자가 티켓을 사거나 양도받으려고 할 때 이 창구에 확인 요청을 보냅니다.

코드에서는 isVerified(address, bytes32)처럼 호출합니다. 첫 번째 값은 확인할 지갑 주소입니다. 두 번째 값은 “어떤 기관이 검증한 결과를 볼 것인가”를 뜻합니다. 이 제품은 UPBIT KOREA attester ID를 기준으로 검증 여부를 확인합니다.

결과가 true이면 검증된 팬으로 보고 구매나 양도를 진행합니다. 결과가 false이면 컨트랙트가 거래를 막습니다.

EAS Attestation

EAS는 검증 기록을 저장하는 기반 시스템입니다. 여기서 attestation은 “누가, 누구에 대해, 어떤 사실을 증명했다”는 기록이라고 이해하면 됩니다.

예를 들어 “UPBIT KOREA가 이 지갑 주소는 검증된 주소라고 증명했다”는 기록이 attestation입니다. 우리 제품은 MVP에서는 EAS를 직접 읽지 않고, 더 간단한 DojangScroll을 통해 true / false만 확인합니다.

다만 나중에 운영자 대시보드나 감사 화면을 만들면 “이 주소가 언제, 어떤 schema로, 어떤 attester에게 검증되었는가” 같은 원본 정보를 EAS에서 더 자세히 확인할 수 있습니다.

0x4200000000000000000000000000000000000021

UPNameRegistry 이름

UPNameRegistry는 지갑 주소와 username.up.id 같은 이름의 연결을 확인하는 곳입니다. 블록체인 주소는 0x...로 시작하는 긴 문자열이라 사용자가 외우기도, 비교하기도 어렵습니다.

그래서 티켓 양도 화면에서 판매자를 0x7a91...4c21로만 보여주면 사용자는 상대방을 신뢰하기 어렵습니다. hyejin.up.id처럼 표시하면 훨씬 자연스럽습니다.

이 기능은 권한을 판단하는 핵심 보안 장치는 아닙니다. 보안 판단은 Dojang Verified Address가 하고, UPNameRegistry는 사용자가 상대방을 더 쉽게 이해하도록 돕는 UX 장치입니다.

Attester ID 신뢰 발행자

attester는 검증을 발행한 주체입니다. 쉽게 말하면 “도장을 찍은 기관”입니다. 같은 지갑 주소라도 누가 검증했는지에 따라 의미가 달라질 수 있기 때문에, 검증 여부를 볼 때는 발행자를 함께 봐야 합니다.

예를 들어 단순히 “이 주소가 검증되었나?”라고 묻는 것보다 “이 주소가 UPBIT KOREA 기준으로 검증되었나?”라고 묻는 편이 더 정확합니다. 이 제품은 한국 야구 티켓 서비스라는 맥락에 맞춰 UPBIT KOREA attester ID를 기본값으로 사용합니다.

0xd99b42e778498aa3c9c1f6a012359130252780511687a35982e8e52735453034

이 제품에 적용한 방식 프론트엔드에는 DojangScroll, EAS, UPNameRegistry 주소를 설정값으로 넣어두었습니다. 사용자가 화면에서 지갑을 연결하면 프론트는 이 주소들을 기준으로 “검증 상태”, “이름 표시”, “explorer 연결” 같은 기능을 붙일 수 있습니다.

컨트랙트 배포 시에는 verifier 주소와 attester ID를 넣습니다. 실제 서비스 모드에서는 verifier 주소로 GIWA의 DojangScroll을 사용합니다. 해커톤 데모 모드에서는 실제 KYC가 없어도 흐름을 보여줄 수 있도록 MockDojangVerifier를 배포합니다. 두 경우 모두 함수 이름은 isVerified로 같기 때문에, 티켓 구매/양도 로직은 그대로 유지하면서 검증 제공자만 바꿀 수 있습니다.

Concept 3

Dojang

Dojang은 블록체인 밖에서 확인된 신뢰 정보를 블록체인 안에서 검증 가능한 형태로 바꾸는 서비스입니다. 쉽게 말하면 “오프체인에서 확인된 사실에 대해 온체인 도장을 찍는 시스템”입니다. 여기서 오프체인은 거래소 KYC, 잔고 확인, 인증번호 확인처럼 블록체인 밖에서 일어나는 일을 뜻하고, 온체인은 스마트 컨트랙트가 직접 읽을 수 있는 블록체인 기록을 뜻합니다.

중요한 점은 Dojang이 사용자의 주민등록번호, 이름, 전화번호 같은 개인정보를 우리 티켓 contract에 저장하게 만드는 시스템이 아니라는 것입니다. 우리 product가 필요한 것은 “이 사람이 누구인가”가 아니라 “이 주소가 신뢰 가능한 검증을 통과했는가”입니다. Dojang은 이 yes/no 판단을 온체인에서 사용할 수 있게 해줍니다.

사용자가 오프체인 검증을 통과합니다. 예를 들어 거래소나 인증 제공자가 사용자의 신원을 확인합니다. 이 단계에서 민감한 개인정보는 오프체인 시스템 안에서 다뤄집니다.
검증 결과가 attestation으로 발급됩니다. Dojang은 EAS 기반 attestation을 사용해 “이 주소는 검증됨” 같은 사실을 GIWA 위에서 확인 가능하게 만듭니다.
앱 또는 contract가 isVerified를 호출합니다. 주소와 attester ID를 넣으면 검증 여부가 반환됩니다. 이때 product는 개인정보 원문을 보지 않고도 정책을 집행할 수 있습니다.
검증된 주소만 티켓 구매와 양도가 가능합니다. contract 단계에서 검증을 강제하므로 프론트 버튼을 우회해도 미검증 주소의 구매나 양도 수락은 실패합니다.
Dojang 발급 데이터 뜻 이 제품에서의 사용 여부
Verified Address 발행자로부터 고객확인을 받은 지갑 주소입니다. 핵심 사용. 구매, 민팅, 양도 수락을 허용할지 판단합니다.
Balance Root 특정 시점의 전체 사용자 잔고 데이터를 merkle tree로 요약한 값입니다. 현재 MVP에서는 사용하지 않습니다. 향후 팬 등급이나 자산 조건 이벤트에 응용 가능합니다.
Verified Balance 특정 시점의 잔고를 검증받았다는 증명입니다. 현재 MVP에서는 사용하지 않습니다. 고가 좌석, 멤버십 혜택 등에 확장 가능성이 있습니다.
Verified Code 오프체인에서 받은 인증번호를 온체인에서 검증할 수 있게 한 데이터입니다. 현재 MVP에서는 사용하지 않습니다. 이벤트 쿠폰, 구단 인증 코드 등에 응용 가능합니다. 
interface IDojangVerifier {
  function isVerified(address addr, bytes32 attesterId)
    external
    view
    returns (bool);
}
이 제품에 적용한 방식 1차 예매, NFT 발급, 2차 양도 수락, NFT 수신자 검증에 모두 Dojang 검증을 넣었습니다. 프론트에서 버튼을 비활성화하는 것은 사용자 경험을 위한 1차 방어이고, contract의 isVerified 검사는 실제 보안 정책입니다. 따라서 사용자가 브라우저 콘솔이나 다른 지갑 도구로 직접 transaction을 보내도 검증되지 않았다면 revert됩니다.

Concept 4

Dojang Contract

Dojang Contract 문서는 Dojang을 구성하는 실제 스마트 컨트랙트와 식별자들을 정리합니다. 여기에는 attester, schema, 조회용 contract가 들어 있습니다. 이 세 가지를 구분하면 Dojang 구조를 훨씬 쉽게 이해할 수 있습니다.

Attester 누가 증명했나

attester는 검증을 발행한 주체입니다. 예를 들어 UPBIT KOREA attester는 특정 주소가 고객확인을 받은 주소라는 사실을 발행할 수 있습니다.

contract가 isVerified(user, attesterId)를 호출할 때 이 attester ID를 함께 넣는 이유는, “아무 검증이나 있으면 통과”가 아니라 “우리가 신뢰하는 발행자의 검증만 통과”시키기 위해서입니다.

Schema 무엇을 증명했나

schema는 attestation 데이터의 형식입니다. Verified Address schema는 bool isVerified 형태로, 어떤 주소가 검증 상태인지 표현합니다.

같은 EAS 기반 attestation이어도 Verified Address, Verified Balance, Verified Code는 서로 다른 의미를 가지므로 schema로 구분합니다.

EAS / Indexer 원장과 색인

EAS는 attestation의 발행, 조회, 취소를 담당하는 원장에 가깝고, AttestationIndexer는 Dojang attestation들을 쿼리하기 쉽게 정리하는 색인 계층입니다.

제품 운영자가 “왜 이 주소가 검증 상태인가”를 더 깊게 추적해야 할 때는 이 계층을 참고할 수 있습니다.

DojangScroll 간편 조회

앱 contract가 매번 EAS 원본 구조를 직접 해석하면 복잡해집니다. DojangScroll은 검증 여부처럼 자주 필요한 Dojang 데이터를 간단한 함수 호출로 읽을 수 있게 해줍니다.

우리 티켓 contract가 직접 연결하는 대상은 이 DojangScroll 형태의 verifier입니다.

항목 문서 기준 값 제품 적용
UPBIT KOREA Attester ID 0xd99b42e778498aa3c9c1f6a012359130252780511687a35982e8e52735453034 한국 사용자의 Verified Address 판정 기본 발행자로 사용합니다.
Verified Address Schema bool isVerified 티켓 구매/양도 가능 여부를 true/false로 판단합니다.
EAS 0x4200000000000000000000000000000000000021 attestation 원본 조회나 운영 감사 기능에서 활용할 수 있습니다.
DojangScroll 0xd5077b67dcb56caC8b270C7788FC3E6ee03F17B9 contract의 verifier 주소로 주입해 isVerified를 호출합니다.
우리 contract가 이 구조를 쓰는 방식 IDojangVerifier 인터페이스는 의도적으로 isVerified(address, bytes32)만 정의합니다. 그래서 실제 배포에서는 GIWA DojangScroll 주소를 넣고, 해커톤 데모에서는 MockDojangVerifier 주소를 넣을 수 있습니다. 프론트와 티켓 로직은 바꾸지 않고 “검증 제공자”만 교체하는 구조입니다. 
constructor(address ticket_, address verifier_, bytes32 attesterId_) {
  ticket = BaseballTicketNFT(ticket_);
  verifier = IDojangVerifier(verifier_);
  attesterId = attesterId_;
}

if (!verifier.isVerified(msg.sender, attesterId)) {
  revert NotVerified(msg.sender);
}

Concept 5

UP ID

UP ID는 긴 지갑 주소 대신 사람이 읽을 수 있는 이름을 제공하는 서비스입니다. 블록체인 주소는 정확하지만 사람이 기억하기 어렵고, UI에 노출했을 때 신뢰를 주기도 어렵습니다. UP ID는 username.up.id 형태의 이름으로 지갑을 찾고 기억하게 해줍니다.

문서 기준으로 UP ID는 Verified Address를 통해 고객확인된 지갑에 제공되고, SBT처럼 양도할 수 없는 형태로 설계되어 있습니다. 즉 UP ID는 단순한 닉네임이 아니라 “검증된 지갑에 붙은, 양도 불가능한 이름”에 가깝습니다. 고객인증이 유효하지 않게 되면 이름과 주소의 연결에도 영향이 생길 수 있으며, grace period 정책도 존재합니다.

주소 기반 UX UP ID 기반 UX
0x7a91...4c21에게 양도 minjun.up.id에게 양도
사용자가 상대방을 식별하기 어렵습니다. 팬, 판매자, 구매자를 사람 이름처럼 표시할 수 있습니다.
실수로 잘못 보낼 위험이 큽니다. 주소와 이름을 함께 표시해 확인 UX를 만들 수 있습니다.

왜 티켓 서비스에 필요한가

티켓 양도는 상대방 신뢰가 중요합니다. 판매자가 0xA13f...91c2로만 보이면 사용자는 누가 파는지 판단하기 어렵습니다. hyejin.up.id처럼 표시하면 팬이 상대방을 더 쉽게 인지할 수 있습니다.

Dojang과의 관계

권한 판단은 Dojang Verified Address가 담당합니다. UP ID는 그 권한 위에 올라가는 사용자 경험입니다. 즉 “구매할 수 있는가”는 Dojang이 결정하고, “누가 구매하거나 양도하는가를 어떻게 보여줄 것인가”는 UP ID가 도와줍니다.

ENS 호환성

UP ID는 ENS 프로토콜 위의 up.id 서브도메인 형태로 제공됩니다. 따라서 ENS를 지원하는 라이브러리와 도구를 사용해 이름 해석 UX를 구현할 수 있습니다.

제품에서 주의할 점

이름은 UX에 유용하지만, contract 정책의 유일한 근거로 삼으면 안 됩니다. 최종 권한 판단은 항상 주소와 Dojang 검증 결과로 해야 합니다. UI에는 이름과 축약 주소를 함께 보여주는 것이 안전합니다.

이 제품에 적용한 방식 현재 프론트 mock에는 minjun.up.id, hyejin.up.id, doyoon.up.id 같은 이름을 판매자와 지갑 이름으로 표시했습니다. 다음 단계에서는 UPNameRegistry 또는 ENS 호환 resolver를 읽어서 실제 주소의 UP ID를 조회해야 합니다. 예매 완료 화면, 내 티켓 카드, 양도 마켓, 입장 QR 화면에서 모두 주소와 UP ID를 함께 보여주면 사용자가 “내가 가진 티켓이 누구에게 속해 있고, 누구에게 양도되는지”를 더 명확하게 이해할 수 있습니다.

Product Mapping

이 개념들이 제품에 들어가는 방식

Proof-of-Fandom Ticket의 핵심은 “검증된 팬만 사고, 검증된 팬끼리만 정가 이하로 양도한다”입니다. GIWA의 각 구성요소는 이 정책을 구현하기 위한 역할을 나눠 갖습니다.

Contract Architecture

우리 Contract 설명

BaseballTicketNFT 티켓 본체

NFT 1개가 좌석 1개입니다. 경기, 좌석, 정가, 양도 마감, 최대 양도 횟수, 사용 상태를 저장합니다. 민팅 시 verified 주소인지 확인하고, 전송 시 공식 마켓인지 다시 확인합니다.

핵심 파일: contract/contracts/ticket/BaseballTicketNFT.sol

PrimaryTicketSale 1차 예매

운영자가 좌석을 등록하고, 팬이 좌석을 구매합니다. 가격, 판매 여부, Verified Address, 1인 구매 제한을 검사한 뒤 티켓 NFT를 발급합니다.

핵심 파일: contract/contracts/sale/PrimaryTicketSale.sol

TicketTransferMarket 2차 양도

티켓 보유자가 정가 이하 가격으로 티켓을 등록하고, 검증된 팬만 구매할 수 있습니다. 실제 NFT 이동은 이 마켓을 통해서만 가능합니다.

핵심 파일: contract/contracts/market/TicketTransferMarket.sol

GateVerifier 입장 처리

게이트 서버가 발급한 EIP-712 서명을 검증합니다. 서명이 유효하고, QR이 만료되지 않았고, 현재 소유자가 맞고, nonce가 재사용되지 않았다면 티켓을 사용 처리합니다.

핵심 파일: contract/contracts/gate/GateVerifier.sol

현재 구현은 해커톤 MVP에 맞춘 구조입니다. 외부 의존성을 줄이기 위해 최소 ERC-721과 AccessControl을 직접 구현했습니다. 실서비스 전에는 OpenZeppelin 기반 재작성, 보안 감사, 멀티시그 권한 관리가 필요합니다.

User Flows

주요 사용자 흐름

1차 예매 흐름

운영자가 좌석을 등록합니다. 경기 ID, 좌석 ID, 정가, 시작 시간, 양도 마감, 1인 제한을 PrimaryTicketSale에 등록합니다.
팬이 좌석을 선택하고 구매합니다. 팬은 purchase(seatKey)를 호출하고 테스트 ETH를 함께 보냅니다.
Dojang 검증을 통과해야 합니다. verified가 아니면 구매 트랜잭션은 revert됩니다.
티켓 NFT가 발급됩니다. 발급된 NFT에는 정가, 좌석, 양도 정책이 저장됩니다.

2차 양도 흐름

보유자가 정가 이하로 등록합니다. TicketTransferMarket.list(tokenId, priceWei)를 호출합니다.
마켓은 가격 상한을 검사합니다. 등록 가격이 NFT의 정가보다 높으면 revert됩니다.
구매자는 verified 주소여야 합니다. verified가 아니면 양도 수락이 실패합니다.
NFT는 공식 마켓을 통해서만 이동합니다. 임의 전송, 외부 거래, 정가 초과 우회를 줄입니다.

입장 흐름

게이트 서버가 QR용 서명을 만듭니다. tokenId, 현재 owner, expiry, nonce, gateId를 포함합니다.
GateVerifier가 서명을 검증합니다. 서명자 권한, 만료 시간, nonce 재사용, 현재 소유자를 확인합니다.
검증이 끝나면 티켓을 사용 처리합니다. NFT 상태가 Used가 되면 재양도와 재사용이 차단됩니다.
